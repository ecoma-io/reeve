# Failure matrix

_What each failure mode does, grounded in code — retry, fallback, skip, rollback, fail, and what a runner would see. Internal companion to the coverage and mutation audit; not a user-facing guide._

Every row names the seam where the behavior lives (file:line), so a claim here can be checked against the source rather than trusted. Columns answer the questions a run has to answer when something above it broke:

- **retry** — does this try the same request again?
- **fallback** — does it try a different model / endpoint / path instead?
- **skip** — does it drop the unit of work and continue?
- **rollback** — does it undo a partial write?
- **fail** — does the run go red (non-zero exit) rather than continue?
- **observable-output** — what a runner sees: an output, a warning, a second attempt, a red job.

A row marked **[GAP]** is behavior that is accidental or unhandled — it exists because nothing handles the case, not because the code decided to. It is called out honestly rather than blessed; the fix is a decision, not a default.

## Provider

The model provider (`src/core/provider.ts`). Classifies one response by `classifyStatus` (`provider.ts:624`): 401/403 → `auth`, 429/5xx → `capacity`, everything else → `protocol`. `rotateModels` walks the roster in order, grounds exhausted models, and throws `AuthenticationFailure` the instant an auth failure is seen (`provider.ts:918`, `provider.ts:698-724`).

| -------------------------------------- | ---------------------------------------- | ------------------------------------------------------- | ----------------------------------------------------------------- | -------- | --------------------------------- | ------------------------------------------------------------------------------------------------- | ------------------------------------------------------- |
| timeout                                | no — never retried                       | yes — next model                                        | yes — grounds only the `model@alias` pair (`provider.ts:341-355`) | n/a      | no                                | failure listed in the run's per-model log; next model asked                                       | `provider.ts:341-355`                                   |

| 403                                    | no — same as 401                         | no                                                      | n/a                                                               | n/a      | **yes** — auth                    | red run                                                                                           | `classifyStatus` `provider.ts:625`                      |
| 429                                    | no — grounded as capacity                | yes — next model                                        | yes                                                               | n/a      | no                                | failure per model; roster exhausted message                                                       | `provider.ts:626`, `provider.ts:737-765`                |

**[GAP] Retry.** No provider failure is ever retried. Across the board the code's answer to a 429/5xx/timeout is "rotate to the next model", and with a one-model roster that is also the end. This is a deliberate design for the free-tier path (`CONTRIBUTING.md` treats roster depth as the answer to weakness) but it means a transient 5xx on a single-model setup is a quiet green run with a failed answer, visible only in the log.

## GitHub

The `@actions/github` octokit client and the shared error classifiers in `src/core/forge.ts`. Non-404 failures generally **throw** and abort the duty; `isMissing` (`forge.ts:863`) treats 404 as "not there"; `isCapacityError` (`forge.ts:885`) is the shared weather side, but nothing in the core retries on it — the caller decides.

| Failure | retry | fallback                                                                  | skip                                            | rollback | fail                                                                                      | observable-output                                                       | evidence                                                                 |
| ------- | ----- | ------------------------------------------------------------------------- | ----------------------------------------------- | -------- | ----------------------------------------------------------------------------------------- | ----------------------------------------------------------------------- | ------------------------------------------------------------------------ |
| 401     | no    | no                                                                        | no                                              | n/a      | **yes** — the duty's own error handling throws                                            | red run                                                                 | `forge.ts:885` does not classify auth; the octokit error propagates      |
| 403     | no    | no                                                                        | no                                              | n/a      | **yes**                                                                                   | red run                                                                 | same                                                                     |
| 404     | no    | no                                                                        | **yes** — contents API read returns "not there" | n/a      | no                                                                                        | empty list / null, treated as cold start                                | `isMissing` `forge.ts:863-864`, `listCorrectionFiles` `forge.ts:940-942` |
| 409     | no    | no                                                                        | no                                              | n/a      | **yes** — thrown unless a caller specifically handles it                                  | red run                                                                 | no 409 handler anywhere in core; propagates                              |
| 422     | no    | yes — review threads move the finding to the summary-only `fallback` list | yes                                             | n/a      | no                                                                                        | `fallback` array in review output, summary notes the unanchored finding | `isUnprocessable` `threads.ts:270`, `syncThreads` `threads.ts:306-329`   |
| 429     | no    | no                                                                        | no                                              | n/a      | **yes** — `isCapacityError` classifies it weather, but nothing here acts on it; it throws | red run                                                                 | `forge.ts:885`; no retry-on-429 in core                                  |

**[GAP] GitHub retry.** `isCapacityError` exists precisely to separate weather from configuration, but nothing in the core retries on it. A sweep uses the classification to exhaust the body and stop (`src/core/sweep.ts:160` is the _provider_ starved check, not a GitHub retry); a non-sweep duty aborts red. That is arguably correct for a GitHub Action — the runner re-runs on a retry schedule — but it is a decision the code does not spell out, and a consumer watching a single green/red transition sees "red, no retry" for a 503 that was momentary.

## State

State is the memory a run carries: the review envelope (`src/duties/review/publish.ts`), the findings ladder (`src/duties/review/findings.ts`), and the disposition mirror. What a rerun, a `force-push`, or an amended commit does to that memory is where most of the interesting failure behavior lives.

| Event                                            | retry | fallback           | skip                                                                                   | rollback | fail | observable-output                                                                      | evidence                                                                  |
| ------------------------------------------------ | ----- | ------------------ | -------------------------------------------------------------------------------------- | -------- | ---- | -------------------------------------------------------------------------------------- | ------------------------------------------------------------------------- |
| identical rerun (same findings)                  | no    | no                 | **yes** — `unchanged` disposition; no write, no comment                                | n/a      | no   | review comment body untouched; `posted`/`replaced`/`unchanged` output says `unchanged` | `renderFingerprint` `publish.ts:466-476`, `classify` `publish.ts:449-454` |
| rerun with changed findings                      | no    | no                 | no                                                                                     | no       | no   | comment replaced in place (same marker)                                                | `postOrReplace` `publish.ts:488-513`                                      |
| force-push (head SHA moved)                      | no    | no                 | **yes** — findings re-derived against the new diff; line-moved findings read `changed` | n/a      | no   | `changed`/`resolved` statuses; summary reflects the new diff                           | `reconcile` `findings.ts:220-264`, `doesNotStand` `findings.ts:226-231`   |
| amended commit (same PR, new SHA)                | no    | no                 | yes, same as force-push                                                                | n/a      | no   | statuses change per new diff                                                           | `findings.ts:226-231`                                                     |
| duplicate event in the same run                  | n/a   | n/a                | **yes** — the run's `seen` set drops an exact duplicate proposed label                 | n/a      | no   | label applied once                                                                     | `enforceLabels` `src/core/enforce.ts:84-90`                               |
| thread list page full / marker never found       | no    | no-nothing written | **yes** — `uncertain` withholds the write                                              | n/a      | no   | `withheld` disposition                                                                 | `findMarked` review publish tests, `classify` `publish.ts:443-446`        |
| envelope corrupt (checksum mismatch / bad shape) | no    | n/a                | yes — treated as absent input, never as a partial read                                 | n/a      | no   | `corrupt` read result; cold start                                                      | `decodeEnvelope`/`encodeEnvelope` `publish.ts`; `envelope.ts:117`         |
| resolved finding reintroduced                    | no    | n/a                | no                                                                                     | n/a      | no   | `reopened` status, not `created`                                                       | `reconcile` `findings.ts:262-264`                                         |

**[GAP] No rollback anywhere.** No seam in the code rolls a partial write back. `syncThreads` deliberately writes creates then updates and, on a non-422 error, throws mid-way — later writes in the loop never happen, and earlier ones stand. The rationale is documented (`threads.ts:276-280`: "the next run's relisting finds no half-written state") — the next run reconciles the half-written state rather than the current one undoing it — but it is a decision a reader should see named, and it means a partially-synced thread set is visible to the author between the failure and the next run.

## How to read a row

A green job is not a successful job. `failure-matrix` rows where `fail` is `no` are green runs that quietly did less — a skipped language, an unanchored finding, an unreadable verdict. The observable-output column is where that quietness becomes visible, and it is the column to keep honest: if a failure is invisible in both logs and outputs, that is the next gap to close, not a success to keep.
